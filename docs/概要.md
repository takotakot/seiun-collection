# 概要設計書: seiun-collection

## 1. プロジェクト概要

- **システム名称:** seiun-collection
- **目的:** 『雀魂-じゃんたま-』内のモード「青雲の志」における、アイテム（お守り・スタンプ・ルーン等）の100%コンプリートを支援する進捗管理・図鑑アプリケーション
- **コンセプト:** ゲームプレイと並行して別画面で進捗をチェック・管理し、ユーザー間で共有可能な攻略メモを残せる補助ツール
- **【重要】イベントの世代に関する前提:**
  - 『雀魂』の「青雲の志」は期間限定イベントであり、開催ごとに「世代」が更新される。
  - 本アプリ設計時点において、過去の「第3世代」などのゲームをプレイすることはできず、現在プレイ可能なのは**「第4世代」**のみ。
  - そのため、データ構造上は複数世代を管理可能にしつつも、現在の表示や管理は**第4世代**を主軸として扱う。

## 2. システムアーキテクチャ

- **フロントエンド:** Astro（Viteベース）＋ React。静的サイト生成（SSG）によりページの外枠を事前にHTMLとして出力し、動的な部分（Firestoreとの通信、所持トグル、攻略メモ編集等）はReactコンポーネント（アイランド）としてブラウザ上で実行する。Firebase Hosting にて静的ファイルとしてホスティングし、低ランニングコスト・低メンテナンスコストを実現する。
- **バックエンド/BaaS:** Firebase (Firebase Client SDK を介して直接通信)
- **データベース:** Cloud Firestore
- **認証:** Firebase Authentication (Googleアカウントログインのみ。進捗データおよび共有コメントの編集権限を制御するため)

## 3. 主要機能要件

### 3.1. 図鑑表示機能

- マスターデータに基づき、全アイテムを「お守り」「スタンプ」「ルーン」のタブ別に一覧表示する
  - **未所持状態:** 暗めの画像で表示する
  - **所持状態:** 通常のカラー画像で表示する
  - **操作:** アイテムの画像自体をタップ（クリック）することで、所持/未所持の状態を直感的に切り替える
- **レアリティ演出:** ゲーム内に準じる

### 3.2. 進捗トラッキング機能

- ユーザーごとの所持状況（ON/OFF フラグ）をシームレスに保存・読み込みする
- 全体および世代ごとのコンプリート率（例: `[ 42 / 105 (40%) ]`）をプログレスバー等で可視化する

### 3.3. 攻略メモ機能

- 各アイテムに対して、全ユーザーで共有・編集できる「攻略メモ（コメント・補足情報）」機能を提供する
  - マスターデータとして用意された固定の「効果テキスト」と、ログインユーザー全員で共有される「攻略メモ（コメント）」を画面上で統合して表示する

### 3.4. 補助ページ

- **プライバシーポリシー:** Google AdSense の審査要件を満たすため、プライバシーポリシーページを別立てで作成する。
- **お問い合わせ窓口:** ユーザーからの連絡用として、Google Forms へのリンクを配置したお問い合わせ窓口ページを別立てで作成する。

## 4. UI/UX デザイン方針

- ゲームのスクリーンショットから復元して再現する

## 5. データモデル設計 (Cloud Firestore)

NoSQL のドキュメント指向データベースとして、全ユーザー共通の「マスターデータ」と「コメント（補足情報）」、ユーザー固有の「進捗データ」を分離して設計する。フロントエンド側でこれらを結合（マージ）してビューを構築する。
アイテム種別（お守り・スタンプ・ルーン）ごとにコレクションを分けるのではなく、単一コレクションに統合して管理することで、将来的な種別の追加やタブの切り替え処理を容易にする。

### 5.1. マスターデータ・コレクション

アルバムに表示する「枠（スロット）」そのものを表現するマスターデータ。

- **パス:** `/items/{generation}_{itemId}` （例: `/items/4_amulet_005`）
- **用途:** アプリケーション内で読み取り専用（Read-only）として配信。
- **スキーマ構成:**
  - `id` (string): ドキュメントID（`{generation}_{itemId}`）
  - `itemId` (string): 実体アイテムID（同じ名前・効果テキストで世代をまたぐ場合は共通。紹介文が変わる場合は別IDにする）
  - `generation` (int): 登場世代 (例: `4`)
  - `order` (int): 図鑑内（アルバム上）の順番
  - `type` (string): アイテムの種別 (`amulet` | `stamp` | `rune`)
  - `name` (string): アイテム名
  - `effect_text` (string): 紹介文/効果テキスト
  - `image_url` (string): アイテムの画像URL（Firebase Cloud Storage 経由で GCS バケット上のデータを参照）
  - `upgrade_from` (string, optional): 強化元となるベースアイテムの `itemId`
  - `upgrade_to` (string, optional): 強化先となるアイテムの `itemId`

### 5.2. ユーザー・コレクション

ユーザーの基本情報および自動クリーンアップ用の最終活動日時を管理する。

- **パス:** `/users/{userId}`
- **用途:** 各ユーザーが自身のデータのみ読み書き可能（Security Rulesで制限）。
- **スキーマ構成:**
  - `userId` (string): ユーザーID
  - `last_active_at` (timestamp): 最終活動日時 (ログイン時、または所持状態の更新時に更新)

### 5.3. ユーザー所持アイテム・コレクション

ユーザーごとのアイテム所持状況を管理する。

- **パス:** `/users/{userId}/collections/{generation}_{itemId}`
- **用途:** 各ユーザーが自身のデータのみ読み書き可能（Security Rulesで制限）。
- **スキーマ構成:**
  - `is_owned` (boolean): 所持状態（true=所持, false=未所持）
  - `updated_at` (timestamp): 最終更新日時

### 5.4. 共有コメント（補足情報）・コレクション

ユーザー全員が共有・編集可能な攻略メモ（コメント）を管理する。1アイテムに対して共通で1つのドキュメントを持ち、楽観的排他ロック（トランザクション）を用いて更新する。

- **パス:** `/comments/{itemId}` （※`itemId` ごとに1つ。世代をまたいで同一アイテムであれば共有される）
- **用途:** ログイン済みユーザーが更新可能。全ユーザーが読み取り可能。
- **スキーマ構成:**
  - `content` (string): 攻略メモ・補足情報テキスト
  - `updated_at` (timestamp): 最終更新日時
  - `updated_by` (string): 最終更新したユーザーのID
  - `updated_by_name` (string): 最終更新したユーザーの表示名
  - `version` (int): 楽観的ロック用のバージョン番号

## 6. 技術的考慮事項

- **非正規化によるクエリの最適化:** RDBにおける「出現世代」と「アイテム」を結合し、`/items/{generation}_{itemId}` という単一のドキュメントとして管理している。これにより、「特定の世代（例: 第4世代）の図鑑をアルバムの順序通りに表示する」という処理が、単一の `generation` フィールドでの絞り込みと `order` フィールドでのソートのみ（1クエリ）で高速かつ安価に完結する。また、`generation_itemId` の形式をドキュメントIDとして採用することで、Firestoreコンソールでの世代ごとのグループ化と前方一致クエリの親和性を高めている。
- **不活動ユーザーデータの自動削除 (バッチ):** 最終活動日時 (`last_active_at`) が187日以上前のユーザーデータをクリーンアップするため、Cloud Scheduler と Cloud Functions を連携した日次クリーンアップバッチを実行する。Firestoreの仕様上、親ユーザーのドキュメント（`/users/{userId}`）を削除してもサブコレクション（`/users/{userId}/collections`）は自動で消えないため、Firebase Admin SDK の `recursiveDelete` を使用してすべての関連データを安全かつ完全に削除する。
- **共有メモの楽観的排他ロック:** 共有の攻略メモは `/comments/{itemId}` に保存され、複数のユーザーが同時に編集した場合の衝突を防ぐため、Firestoreのトランザクション（`runTransaction`）機能を使用する。クライアントが読み込んだ際の `version` を更新条件とし、古いバージョンに基づく更新要求は自動的に失敗となる。
- **画像アセットの管理:** 画像データは実体として Google Cloud Storage (GCS) に配置し、クライアントからのアクセス性・セキュリティ管理を容易にするために Firebase Cloud Storage の機能（SDK / Rules）を活用して配信する。
- **強化アイテムの相互参照:** `upgrade_from` と `upgrade_to` を持たせることで、UI上で「強化前・強化後」の関連性を容易に表示・ナビゲーションできるようにする。
