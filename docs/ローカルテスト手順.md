# ローカル検証・テスト手順マニュアル

本書は、開発者がローカル環境で「青雲コレクション」アプリの全機能（Google認証、進捗状況の管理・同期、共有攻略メモのトランザクション、定期実行の不活動アカウント削除バッチ）を安全に実行・検証するための詳細な手順を記載しています。

## 1. 事前準備

ローカル環境にてテストを行うには、以下のツールが必要です。

- **Node.js**: `v24.16.0` 以上 (プロジェクト `.node-version` に準拠)
- **Firebase CLI**:
  エミュレータを実行するために、事前にグローバルインストールを行ってください。
  ```bash
  npm install -g firebase-tools
  ```

## 2. 依存関係のインストール

アプリケーションのルートディレクトリ、および `functions` ディレクトリ配下でそれぞれパッケージをインストールします。

```bash
# アプリケーション共通の依存関係インストール
npm install

# Cloud Functions 用の依存関係インストール
cd functions
npm install
cd ..
```

## 3. Firebase エミュレータの起動

プロジェクトは、実環境の Firebase リソースを消費・破壊しないために **Firebase Local Emulator Suite** で完全仮想化して動作可能です。

以下のコマンドを実行してエミュレータを起動します。

```bash
firebase emulators:start
```

起動後、ターミナル上に各種コンソールのポートが表示されます。
- **Emulator Suite UI (GUI 管理画面)**: `http://127.0.0.1:4000` (またはターミナルに表示されたポート)
- **Firestore Emulator**: `127.0.0.1:8080`
- **Auth Emulator**: `http://127.0.0.1:9099`

ブラウザで `http://127.0.0.1:4000` にアクセスすることで、ローカル上のデータベースの状態や認証済みユーザーの一覧をリアルタイムに確認・操作できます。

## 4. テスト用初期マスタデータの流し込み (シーディング)

エミュレータが起動しているのを確認したら、**別のターミナルタブ**を開き、以下のコマンドを用いてテスト用のマスタデータ（お守り、スタンプ、ルーンの全11件）を注入（シーディング）します。

```bash
# 接続先をローカルエミュレータに強制指定
export FIRESTORE_EMULATOR_HOST="127.0.0.1:8080"

# シードスクリプトの実行
node scripts/seed.js
```

`Successfully` と表示、または各キューへの追加ログが出れば成功です。
Firebase エミュレータ UI (`http://127.0.0.1:4000`) の Firestore 画面を開き、`items` コレクションの配下にデータが正常に投入されているか確認します。

## 5. Astro 開発サーバーの起動

エミュレータへの接続用環境変数を付与した状態で、Astro クライアントサーバーを起動します。

```bash
# クライアントSDK接続をエミュレータに迂回する環境変数
export PUBLIC_FIREBASE_USE_EMULATOR="true"

# Astroを開発モードで起動
npm run dev
```

ブラウザで [http://localhost:4321](http://localhost:4321) を起動します。

## 6. ユースケースに沿った機能検証方法

### 6.1. Google 認証テスト
1. 画面上部の「Googleでログイン」ボタンを押します。
2. エミュレータ専用のダミー認証ポップアップ、または入力欄が現れます。
3. 任意のメールアドレス（例: `test@example.com`）やユーザー名を入力してログインをシミュレートしてください（実Googleアカウントの認証キーや安全情報を通さずに、エミュレータ上でユーザーIDが作成されます）。

### 6.2. 所持チェック＆活動日時の間引き書き込み制御テスト
1. アルバム一覧（お守り・スタンプ・ルーン）から任意のアイテムのアイコン（画像）部分をクリックします。
2. 未所持状態（暗転）から、カラー画像に変化し「所持」リボンが追加されることを確認します。
3. エミュレータ UI の Firestore 画面で、以下のようにデータが作成されたことを確認してください。
   - `/users/{あなたのUID}/` ドキュメント内の `last_active_at`
   - `/users/{あなたのUID}/collections/{generation}_{itemId}` ドキュメント内の `is_owned: true`
4. 次に他のアイテムのトグルを何度もクリック（連打、切り替え）します。
5. **検証ポイント**: 所持コレクション `/collections` 内のドキュメントのフラグは即時更新されますが、プロフィール親ドキュメント `/users/{あなたのUID}` の `last_active_at` は、ミリ秒単位で書き換わらずに保持（168時間以内のため書き込み処理をスキップ）されることを確認します。これで無駄なコスト削減の仕組みが正しく働いていることが実証されます。

### 6.3. 共有Wiki攻略メモの楽観的排他ロックテスト
1. アイテムの「詳細・メモ」リンクをクリックし、右側の詳細パネルを表示します。
2. 攻略メモ欄に任意の文章を入力し「攻略メモを更新する」をクリックします。
3. エミュレータ UI の `/comments/{itemId}` にデータが書き込まれ、`version: 1` となっていることを確認します。
4. **衝突排他テスト**:
   - 別ブラウザ（プライベート窓など）または別のブラウザタブで同じURLにアクセスし、同じお守りの詳細ペインを開きます（このとき、両方のタブで画面上の `version` は共通の値となっています）。
   - タブAで「メモパターンA」を送信します。保存に成功し、DBのバージョンは `+1` されます。
   - すかさずタブBに戻り、古い状態の画面から「メモパターンB」として「攻略メモを更新する」ボタンをクリックします。
   - **検証ポイント**: タブBの画面上に「**他のユーザーによってメモが同時に編集されました。再度取得された最新データを確認して、やり直してください**」という内容のエラーダイアログが表示され、先祖返りの上書き事故が防止されることを確認します。
