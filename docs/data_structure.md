# データベースデータ構造定義書 (Cloud Firestore)

本アプリケーションにおける Cloud Firestore のデータモデル設計、ID命名規則、楽観的排他ロック、および不活動ユーザーデータ削除に伴う最適化手法について定義する。

## 1. コレクション構成一覧

Firestore ではクエリの効率化とクライアント側でのマージ処理を最小限に抑えるため、**「出現世代」と「アイテム詳細」を非正規化したコレクション構成**を採用する。

| コレクション | パス | 用途 | 権限 (Security Rules) |
| :--- | :--- | :--- | :--- |
| **マスターデータ** | `/items/{generation}_{itemId}` | 各世代の図鑑スロット情報 | 全員: Readのみ |
| **共有攻略メモ** | `/comments/{itemId}` | ログインユーザーが共有・共同編集するWikiメモ | 全員: Read / ログイン者: Write |
| **ユーザー** | `/users/{userId}` | ユーザー基本情報・最終活動日時管理 | 本人: Read・Write |
| **ユーザー所持** | `/users/{userId}/collections/{generation}_{itemId}` | ユーザーのアイテム所持状況フラグ | 本人: Read・Write |

---

## 2. 図鑑の枠とアイテムの同一性定義

本アプリケーションにおける「図鑑の枠（スロット）」と「アイテムの同一性」についての定義をまとめる。

### 2.1. 図鑑（アルバム）について
ゲーム内の図鑑（アルバム）画面の表示に準拠する。図鑑は「お守り」「スタンプ」「ルーン」などのカテゴリ（タブ）ごとに分かれており、アイテムごとに一定の並び順（表示枠）が存在する。

### 2.2. アイテムの「同一性」定義
基本原則として、**「ゲーム内の図鑑における1つの枠（スロット） ＝ アプリ上の1つのアイテムID（同一アイテム）」** として扱う。

1. **完全一致**
   文章（効果テキスト）・絵柄（画像）・レアリティがすべて同一であり、図鑑上で同じ枠に配置されるものは「同一アイテム」とみなす。
2. **「強化」による別枠アイテム**
   一部のお守りには、上矢印（↑）アイコンなどが付与された「強化版」が存在する。これらが**図鑑上で元のアイテムとは別の枠に配置されている場合**は、アプリ上でも「別アイテム（別の itemId）」として扱う。（例: `amulet_005`, `amulet_006`）
   ただし、元のアイテムと強化後のアイテムは関連しているため、マスターデータ側で相互リファレンス（`upgrade_from`, `upgrade_to`）を持たせ、UI上で関係性を辿れるようにする。
3. **図鑑で区別されない強化（2回目以降の強化や隠しステータス等）**
   1回強化と2回以上の強化が図鑑上で区別されない（別の枠として表示されない、あるいは見た目が変わらない）場合、図鑑としてのコレクション管理上は**「同一のアイテム」**として扱い、進捗状況（所持フラグ）は分けずに管理する。

## 3. 各コレクションのスキーマ定義

### 3.1. マスターデータ (`items` コレクション)
アルバムに表示する「枠（スロット）」そのものを表現するマスターデータ。

- **パス:** `/items/{generation}_{itemId}`
  - 例: `/items/4_amulet_005`
- **ID命名規則 (`generation_itemId`):**
  - **メリット1 (コンソール視認性):** Alphabetic順でソートされた際に世代（`4_` など）ごとに整列されるため、Firestoreコンソールでのデータ確認が容易。
  - **メリット2 (インデックス節約):** 世代の絞り込み（例: 第4世代のみ取得）を、セカンダリインデックスを作成せずとも、ドキュメントIDの前方一致範囲クエリ（`startAt("4_").endAt("4_\uf8ff")`）で実現可能。
- **スキーマ:**
  - `id` (string): ドキュメントID（`{generation}_{itemId}` と同一）
  - `itemId` (string): 実体アイテムID。同じ名前・効果テキストで世代をまたぐ場合は共通、紹介文や効果が変わる場合は別IDにする。
  - `generation` (int): 登場世代 (例: `4`)
  - `order` (int): その世代の図鑑内での並び順 (1-indexed)
  - `type` (string): アイテム種別 (`amulet` | `stamp` | `rune`)
  - `amulet_kind` (string, optional): お守りの種類 (`normal` | `rare` | `super_rare` | `ultra_rare` | `ghost`) ※第4世代かつ `type === 'amulet'` で設定。スタンプ・ルーンでは未使用
  - `name` (string): アイテム名
  - `effect_text` (string): 紹介文・効果テキスト
  - `image_url` (string): 画像URL (Firebase Cloud Storage 参照パス)
  - `upgrade_from` (string, optional): 強化元となるベースアイテムの `itemId`
  - `upgrade_to` (string, optional): 強化先となるアイテム of `itemId` (カードに「+」マークが付く同名系の強化用)
  - `relates_from` (string, optional): 特殊な関連・進化元となるアイテムの `itemId` (名前が変わる特殊アップグレード等用。カードに「+」マークは付かない)
  - `relates_to` (string, optional): 特殊な関連・進化先となるアイテムの `itemId` (名前が変わる特殊アップグレード等用。カードに「+」マークは付かない)
  - `recipe_sources` (array of string, optional): 合体進化（4枚集めて新しい1枚にする）の素材となる4つのアイテムの `itemId` リスト（進化後のアイテム側が保持）
  - `recipe_target` (string, optional): 合体進化して生まれる先のアイテムの `itemId`（進化前の素材アイテム側が保持。一対多の関係を簡潔に表現）

### 3.2. 共有攻略メモ (`comments` コレクション)
全ユーザーで共同編集するWiki形式のメモ。

- **パス:** `/comments/{itemId}` （※`itemId` ごとに1つ。世代をまたいで同一アイテムであれば共有）
- **スキーマ:**
  - `content` (string): 攻略メモ本文
  - `updated_at` (timestamp): 最終更新日時
  - `updated_by` (string): 最終更新ユーザーID (Firebase Auth `uid`)
  - `updated_by_name` (string): 最終更新ユーザー表示名
  - `version` (int): 楽観的ロック用のバージョン番号

### 3.3. ユーザー (`users` コレクション)
ユーザー情報および不活動削除バッチ用のメタデータを管理。

- **パス:** `/users/{userId}`
- **スキーマ:**
  - `userId` (string): ユーザーID
  - `last_active_at` (timestamp): 最終活動日時

### 3.4. ユーザー所持 (`user_collections` サブコレクション)
ユーザーが特定世代 of 各アイテム枠を取得したかのフラグを管理。

- **パス:** `/users/{userId}/collections/{generation}_{itemId}`
- **スキーマ:**
  - `is_owned` (boolean): 所持状態 (true=所持, false=未所持)
  - `updated_at` (timestamp): 所持状況の最終更新日時

## 4. 技術的制御と最適化設計

### 4.1. `last_active_at` の書き込みコスト削減 (クライアント制御)
「アイテムを所持チェックするたびに `last_active_at` を更新する」と、Firestore の書き込み（Write）コストが跳ね上がる。これを防ぐために以下の制御を行う。

#### 更新の間引き制御
1. クライアントアプリ起動時（またはログイン時）、自身の `/users/{userId}` から `last_active_at` を取得し、ローカル（メモリやLocalStorageなど）に保持する。
2. アプリ上で操作（所持状態のトグルなど）が行われた際、以下の判定を行う。
   - **`現在時刻 - last_active_at > 7日`** (168時間) である場合のみ、所持データの更新と同時に `/users/{userId}` の `last_active_at` を `serverTimestamp()` で更新する。
   - 差分が7日以内の場合は、`/users/{userId}` への書き込みは行わず、所持データ（サブコレクション）のみを更新する。
3. これにより、アクティブなユーザーによる不要な書き込みを大幅に削減（最大でも7日に1回に抑制）しつつ、187日の不活動判定を高い精度で担保する。

### 4.2. 楽観的排他ロック (Optimistic Concurrency Control)
共有攻略メモの同時編集衝突を防止する。

#### 更新フロー
1. クライアントが `/comments/{itemId}` のドキュメントを読み込み、画面に表示する（この時の `version` 値を保持）。
2. ユーザーが編集を終えて保存する際、Firestore のトランザクション（`runTransaction`）を使用する。
3. トランザクション内でドキュメントを再読み込みし、ステップ1で保持していた `version` とデータベース上の現在の `version` が一致しているか検証する。
   - **一致している場合:** `version` を `+1` し、新たな内容でドキュメントを更新してコミット。
   - **不一致の場合:** 他のユーザーが先に更新したとみなし、トランザクションを失敗させる（画面に「他のユーザーによって更新されました」とエラーを表示し、リロードを促す）。

### 4.3. 187日以上未アクセスの自動クリーンアップ
- **仕組み:** Cloud Scheduler (Cron) + Cloud Functions (バッチ) を日次で実行する。
- **処理:**
  1. `last_active_at` が 187日前より古いドキュメントを `/users` コレクションからクエリ。
  2. 対象ユーザーの Firebase Auth アカウントを削除。
  3. Firestore Admin SDK の `recursiveDelete` を呼び出し、対象ユーザー of `/users/{userId}` ドキュメントおよびサブコレクション `/users/{userId}/collections` 以下の全データを完全に削除する。
